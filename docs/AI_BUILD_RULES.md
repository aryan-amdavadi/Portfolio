This document defines the engineering and design rules for this portfolio.

You are not authorized to redesign the portfolio architecture on your own.

Before implementing a requested phase:

1. Inspect the current repository.
2. Understand existing components.
3. Preserve working systems.
4. Implement only the requested phase.
5. Avoid unrelated refactoring.
6. Do not fabricate content, metrics, achievements or experience.
7. Do not replace established design decisions without explicit instruction.
8. Reuse existing components where appropriate.
9. Keep 3D logic isolated from ordinary UI.
10. Keep animations reusable.
11. Maintain responsive behavior.
12. Maintain reduced-motion behavior.
13. Maintain low-end fallback behavior.
14. Run lint.
15. Run typecheck.
16. Run production build.
17. Verify the changed functionality.
18. Create the phase-specific Git commit.

Never solve a design problem by adding more visual effects.

Every animation must have a purpose.

Every 3D object must communicate something.

Every project must be represented by real information.

Never invent:
- users
- revenue
- performance statistics
- clients
- awards
- employment
- achievements
- project metrics

If information is missing, create a clearly marked data placeholder.

The portfolio's central identity is:

"I am a developer who solves real-world problems."

The portfolio should feel:
- intelligent
- technical
- professional
- business-minded
- cinematic
- premium
- minimal
- original

It should NOT feel:
- generic
- template-based
- cyberpunk
- excessively neon
- overloaded with glassmorphism
- like a Three.js demo
- like an AI-generated portfolio template.

The 3D experience must enhance the story rather than replace it.
